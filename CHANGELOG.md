## 0.97.1 — 2026-10-06

### Fixed

- **Auth callbacks can return `status(...)` on Elysia 2.0.0-beta.21** (`StatusReturn`)
  `StatusReturn` picked `code` from Elysia's `ElysiaStatus`, which Elysia 2.0.0-beta.21 removed (the status box now carries `status` and `response`). Every `status(...)` returned from an auth callback was a type error on that Elysia. `StatusReturn` now picks `status` and `response`, which every Elysia 2 beta has. Runtime behavior is unchanged. Also shipped as 0.85.1 for consumers pinned to 0.85.

### Internal

- **Generated declarations reordered without changing any type** (`createAuthApplications`, `oidcProviderRoutes`)
  The generated declarations of these exports list the same members in a different order (an optional `code` field moved within one object type). The types are identical; nothing to change in consuming code.

## 0.95.0 — 2026-09-27

### Breaking

- **Replace permanent MFA lockouts with durable timed attempt budgets, independent recovery-code limits, and atomic recovery-code consumption. Previously locked accounts can authenticate again.** (`MFAStore`, `MfaEnrollment`, `mfaChallenge`, `MfaConfig`)
  _Migration:_ Run the mfa migration block before upgrading servers. Custom MFAStore implementations must add atomic claimCodeAttempt, completeCodeChallenge, and resetCodeAttempts methods. Handle HTTP 429 mfa_rate_limited responses with Retry-After and retryAfterMs. Recovery codes are opaque strings, not fixed eight-character values.
- **Make TOTP setup and verification retry-safe across instances; preserve recovery codes when adding devices, resume pending QR codes, and include device labels in authenticator account names.** (`MFAStore`, `MfaEnrollment`, `TotpMfaFactor`, `withMfaFactors`)
  _Migration:_ Custom MFAStore implementations must implement atomic saveTotpEnrollment. Setup now resumes pending enrollments. TOTP verification preserves existing recovery codes; an empty backupCodes array means existing codes remain unchanged. First-issuance responses can be replayed for ten minutes after a valid TOTP using an encrypted receipt in factor JSON. No SQL migration is required.
- **Isolate SMS sign-in codes and resend cooldowns by pending session and phone. Preserve concurrent users codes and return structured resend timing. Keep a separate account delivery budget (default ten attempts per five minutes).** (`createAuthApplications`, `MFAStore`, `MfaConfig`, `mfaChallenge`, `mfaRoutes`)
  _Migration:_ Run mfa/0008_scoped_sms_challenges before rollout. Custom MFAStore implementations must implement getSmsChallengeStore with durable atomic state per user, pending session, and factor, and support the sms_send attempt budget. SMS codes issued by old servers must be requested again after upgrading.

### Added

- **Allow a default authenticator label resolved from the signed-in user when the submitted name is blank. Preserve custom names and pending enrollments.** (`MfaConfig`, `mfaTotpRoutes`)

### Fixed

- **Use the chosen method name in TOTP QR account labels instead of internal user and factor identifiers. Preserve existing secrets and factor IDs.** (`mfaTotpRoutes`)
- **docs/PERSISTENT-CREDENTIALS.md no longer mixes SQLite and PostgreSQL or gives stale migration advice: it has one complete PostgreSQL + Drizzle path and one SQLite path, the exact route list and session cookie, a typed guard, and current migration steps, and its code is typechecked against dist (check:guide) and run end to end in tests.**
- **Preserve pending MFA login cookies during authentication-status and protected-route checks. Read-only session resolution no longer expires browser cookies, preventing delayed unauthenticated responses from erasing a newer login. Expired server sessions are still removed, and pending sessions remain unauthenticated.** (`protectRoutePlugin`, `requireAuthPlugin`)

## 0.93.0 — 2026-09-26

## 0.92.0 — 2026-09-26

### Added

- **Passkey management: `GET`, `PATCH` (rename) and `DELETE` on `/auth/webauthn/credentials` for the signed-in user's own passkeys. Passkeys now have a `name` (webauthn migration 0003): the one passed at registration, or the provider's name from its AAGUID (iCloud Keychain, Google Password Manager, Windows Hello, 1Password…). `hasOtherSignInMethod` can protect the last passkey. The client gains `passkeys.rename`, a working `passkeys.list`, `runPasskeyRegistration(client, { name })` and `runPasskeyAuthentication` for a sign-in button.** (`AuthClientRoutes`, `PasskeySummary`, `WebAuthnConfig`, `WebAuthnCredential`, `WebAuthnCredentialStore`, `WebAuthnRegistrationResult`, `createAuthClient`, `defaultPasskeyName`, `runPasskeyAuthentication`, `runPasskeyRegistration`, `useUpgradeToPasskey`, `webauthnCredentialsTable`, `webauthnRoutes`)
- **Sessions record how and where they signed in: `signInMethod` (provider name, `passkey`, `password`, `magic_link`, `otp`, `sso`) and the User-Agent (sessions migration 0003). `GET /auth/sessions` returns them with a coarse `device` (`{ browser, os }`) via `describeUserAgent`; pass the callback's new `request` to `instantiateUserSession` to record OAuth sign-ins. The client's `sessions.list` now returns the array the server sends.** (`CallbackContext`, `InsantiateUserSessionProps`, `SessionData`, `createAuthClient`, `describeUserAgent`, `instantiateUserSession`, `oidcSsoRoutes`, `sessionRoutes`, `useSessions`)
- **Sign-in identities: several provider accounts can open one user. New `identities` config mounts `GET /auth/identities` and `DELETE /auth/identities/:id` (never removes the last way in unless `hasOtherSignInMethod` says so); `linkCallbackIdentity` links the OAuth callback's account to the signed-in user from `onLinkIdentity` and throws `AuthIdentityConflictError` when another user already owns it, so `onLinkIdentityConflict` finally runs. Postgres/Neon and in-memory stores; migration block `identities` creates `auth_identities` (compatible with existing app tables and the CLI importer) with a unique provider+subject index.** (`AuditEventType`, `AuthConfig`, `AuthIdentity`, `AuthIdentityStore`, `BlockName`, `IdentitiesConfig`, `authIdentitiesTable`, `createAuthApplications`, `createInMemoryIdentityStore`, `createNeonIdentityStore`, `createPostgresIdentityStore`, `identityRoutes`, `linkCallbackIdentity`, `resolveCallbackIdentity`)
